# Fixes — 2026-06-03 (SEO detection empty tables + Vercel deploys failing)

## 1. seo_opportunities / seo_regression_alerts were empty (0 rows) — FIXED in code

**Root cause (deeper than the threshold theory):** the sync edge function
`supabase/functions/sync-gsc-ga4/index.ts` calls two RPCs —
`detect_seo_opportunities(impression_threshold, ctr_threshold)` and
`detect_seo_regressions(days, position_drop_threshold, ctr_drop_threshold)` — but **those functions
were never defined in any migration** (the only migration defined differently-named helpers,
`seo_opportunity_score` and `detect_seo_regression`). So every run, the `rpc(...)` calls errored,
the error was swallowed by `console.error`, and nothing was ever inserted.
Secondary issue (also fixed): detection must aggregate over a **rolling window**, not per
keyword-per-day — single-day impressions rarely reach 500.

**Fix:** new migration `supabase/migrations/20260603_seo_detection_functions.sql` defines both RPCs
with the exact parameter names the edge function passes, and:
- `detect_seo_opportunities` aggregates `seo_gsc_daily` over the last `window_days` (default 28),
  computes windowed impressions + clicks-weighted CTR + impressions-weighted position, flags
  `imp >= impression_threshold AND ctr < ctr_threshold`, retires stale rows, and upserts current ones.
- `detect_seo_regressions` compares the recent window vs the prior window of equal length (default
  7d each), flags `position_drop` (recent avg position worse by > threshold) and `ctr_drop`
  (recent CTR < prior * (1 - threshold)), requiring a meaningful prior baseline
  (`min_baseline_impressions`, default 50), and upserts alerts.
- Both `RETURN` the affected rows so the edge function's `data.length` logging works.

No edge-function change needed (parameter names already match).

**To apply:** run the migration against the Supabase project, then trigger one sync.
```bash
supabase db push        # or paste the migration into the Supabase SQL editor
# then invoke the sync function once (or wait for the cron) to populate the tables
```
Note: this fix is logically validated but was authored without live DB access — apply to staging
first if available, then confirm `select count(*) from seo_opportunities;` is non-zero after a sync.

## 2. Vercel deployments all failing — OWNER config actions (two independent causes)

### a) GitHub Actions: "The specified token is not valid"
The `VERCEL_TOKEN` repo secret is invalid/expired. **I can't read/write GitHub secrets.**
Fix: regenerate at https://vercel.com/account/tokens → update the `VERCEL_TOKEN` repo secret
(Settings → Secrets and variables → Actions).

### b) Vercel Git integration: "No Next.js version detected … Root Directory"
This is a **Root Directory mismatch**, made worse by the repo's two unrelated histories:
- On **`main`**, the Next.js app lives in **`dashboard/`** (next 16.2.6); there is **no root
  `package.json`**. A Vercel project building `main` with Root Directory = repo root therefore sees
  no Next.js → fails.
- On branch **`claude/magical-keller-AroZC`**, the Next.js app (`seo-automation-dashboard`,
  next 14.1.4) is at the **repo root** with a `vercel.json`.

**Fix per Vercel project** (Dashboard → Project → Settings → General → Root Directory):
- The project meant to deploy **main's dashboard** → set **Root Directory = `dashboard`**.
- The project meant to deploy **this branch's SEO dashboard** → Root Directory = `` (root), and set
  its **Production Branch** to `claude/magical-keller-AroZC` (or whichever branch holds the root app).
- Two Vercel projects (`seo-dashboard`, `wnlq-9-content-seo`) auto-building the **same repo** on every
  push is noisy and is why "20+ deployments in ERROR." Decide which project owns which app/branch and
  **disable auto-deploy** (or scope the Production Branch + Ignored Build Step) on the other.

> Net: regenerate `VERCEL_TOKEN`, set each project's **Root Directory** (and Production Branch), and
> de-duplicate the two projects. These are dashboard settings only the owner can change.
